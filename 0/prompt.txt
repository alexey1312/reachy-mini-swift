# App Store + Hugging Face + Remote Access («Your Reachies») + виджеты — Phase 2 finale

## Context

Последний крупный блок Фазы 2. По результатам ресёрча (исходники демона 1.9.0/main, открытый
central-сервер, официальные приложения Pollen) фича состоит из четырёх частей:

1. **Магазин приложений робота** — HF Spaces с тегом `reachy_mini_python_app`; демон сам
   скачивает snapshot и ставит `uv pip install` в общий venv. Клиент — обёртка над `/api/apps/*`.
2. **Вход в Hugging Face** — нативный, на телефоне, «в 1 кнопку» (как в официальном
   iOS-приложении, которое показывает вход до подключения к роботу ⇒ OAuth у него клиентский):
   `ASWebAuthenticationSession` (делит куки Safari) + наш зарегистрированный **public OAuth-app
   HF** (client_id без секрета, custom-scheme redirect, PKCE). Токен — в **Keychain**
   (ADR-0001: «credentials в Keychain, инжектятся централизованно ReachyKit»). Привязка робота =
   `POST /api/hf-auth/save-token` по LAN (демон валидирует через whoami и хранит у себя).
   Браузерный OAuth-флоу демона (редирект на `reachy-mini.local`) **не используем** — не нужен.
   Fallback без OAuth-app: вставка PAT.
3. **Remote-доступ «Your Reachies»** — central-сервер = публичный HF Space
   `https://pollen-robotics-reachy-mini-central.hf.space` (исходники открыты; env
   `REACHY_CENTRAL_URL`). Робот и клиент аутентифицируются `Authorization: Bearer <HF-токен>`;
   робот-producer виден только владельцу токена. Сигналинг — тот же протокол GStreamer
   webrtcsink, что у нас на :8443 (`SignalingMessage`), но поверх **SSE (`GET /events`) +
   `POST /send`**. Дальше обычный WebRTC (STUN-only, **TURN нет**). Удалённо HTTP-API демона
   **недоступен**: управление — data-канал `"data"` (JSON-команды `wake_up`, `set_target`,
   `get_state`… + JSON-RPC `apps.*`), телеметрия — unreliable-канал `"pose"` (~30 Hz, `seq`).
4. **Виджеты** — App Group + App Intents + widget-extension «запустить приложение робота».

Решения пользователя: всё в одной ветке `claude/hugging-face-oauth-app-store-5hu2g2`
(от `main@9404f7d`); вход — 1 кнопка + PAT-fallback; каталог — только демон (без кэш-API сайта).
Conventional commits, коммит на milestone.

## Контракт демона `/api/apps/*` (1.9.0; факты, проверенные по исходникам)

- `AppInfo{name, source_kind: hf_space|dashboard_selection|local|installed, description, url?, extra}` —
  `extra` = сырой JSON HF Space. **POST /install требует весь `AppInfo` дословно** → домен
  хранит оригинальный generated-объект для round-trip.
- **Ловушка идентичности**: catalog `name` = слаг Space, `extra["id"]` = `"owner/repo"`;
  installed `name` = имя pip entry-point (может отличаться!) — lifecycle-роуты ключуются по
  **installed**-имени. Сопоставлять через `extra["id"]` + нормализацию.
- `install|remove|update` → сразу `{"job_id"}`; **провал job — не HTTP-ошибка** (только
  `JobInfo.status == failed`). `job_id` не переживает рестарт демона (404).
- WS `/api/apps/ws/apps-manager/{job_id}` (не в spec): неизвестный id →
  `{"error":"Job ID not found"}`+close; каждая новая строка лога — голый текстовый фрейм, затем
  JSON `{command,status,logs:[новые]}`; закрывается после done|failed; **просыпается только на
  новых логах** → может молча висеть — всегда в паре с поллингом `job-status` (500 ms; таймауты:
  install 60 s, remove 90 s, stale 90 s).
- `current-app-status` → **200 с литеральным `null`**, когда idle. `stop-current-app` повторно →
  400. `start-app` при занятом слоте → 400. `no-evict` — только main (404 на 1.9.0), не используем.
  `GET /api/daemon/robot-app-lock-status` → `{state: free|local_app|remote_session, holder_name?}`.
- `check-updates?force=` — кэш 5 мин на демоне.
- UI-метаданные из `extra`: `cardData{title, emoji, colorFrom, colorTo, short_description}`,
  `author`, `likes`, `private`; official = `author == "pollen-robotics"`. Тумбнейлов нет —
  эмодзи на градиенте.
- hf-auth: `GET /hf-auth/status → {is_logged_in, username?}` (whoami на каждый вызов — медленно
  → кэшировать); `POST /hf-auth/save-token {token}` (400 если невалиден); `DELETE /hf-auth/token`;
  `GET /hf-auth/central-robot-status → {available, robots[], reason?}` (LAN-прокси central без
  выдачи токена); `GET /hf-auth/relay-status → {state: stopped|waiting_for_token|connecting|connected|reconnecting|error, is_connected}`;
  `POST /hf-auth/refresh-relay`. Все ответы кроме save-token в спеке `additionalProperties: true`
  → generated отдаёт `OpenAPIObjectContainer`, декодировать руками (паттерн `kinematicsInfo()`).

## Контракт central-сервера (из `app.py` Space `pollen-robotics/reachy_mini_central`)

- Auth: только `Authorization: Bearer` (валидация через `whoami-v2`, кэшируется). Rate limit
  1200 req/60 s на токен. `GET /health` — без auth.
- `GET /api/robot-status` → `{robots: [{peerId, robotName?, busy, activeApp?, meta{name, transport,
  hardware_id?, install_id?}, last_seen_age_seconds}]}`. **Онлайн = присутствие в списке**
  (lease 30 s, heartbeat робота ~10 s). `peerId` меняется на каждом реконнекте relay —
  стабильный ключ: `install_id ?? hardware_id ?? peerId`; `hardware_id` = тот же 16-hex, что
  `GET /api/daemon/hardware-id` (правило 4 — join LAN↔central по нему).
- Сигналинг: `GET /events` (SSE, `data:`-строки; `welcome{peerId, username,
  recommended_heartbeat_interval_seconds}` → `list{producers[]}` → дельты `peerStatusChanged`,
  `sessionStateChanged`; `ping` каждые 30 s — тишина >30 s = мёртвый стрим). Исходящее —
  `POST /send`, **ответ приходит телом POST** (`sessionStarted{sessionId}` /
  `sessionRejected{reason: robot_busy, activeApp}` / `error{details}`). Клиент представляется
  `setPeerStatus{roles:["listener"], meta:{name}}` — `meta.name` виден владельцу как `activeApp`.
- **Робот — offerer**: по SSE приходит `peer{sessionId, sdp:{offer}}` → отвечаем
  `peer{sdp:{answer}}`; ICE `peer{ice:{…}}` в обе стороны; **пустой `candidate` =
  end-of-candidates — дропать** (WebRTC.framework кидает на нём). `endSession{reason:
  robot_busy|robot_busy_local|robot_busy_local_app|local_app_started|install_id_takeover}` —
  обрабатывать обе формы отказа (`sessionRejected` и `endSession`).
- ICE: STUN-only `stun:stun.l.google.com:19302`, **TURN нет** — симметричный NAT/CGNAT не
  соберётся; таймаут → подсказка «подключитесь к одной сети».
- Медиа: H.264 CB 3.1 видео + **двунаправленный** Opus (робот форсирует `sendrecv`).
- Data-каналы: `"data"` (reliable, открывает робот) — JSON-команды
  (`{"type": "wake_up"}`, `get_state → {state:{head[16], antennas, body_yaw, motor_mode,
  is_move_running}}`, `set_target`, volume, robot-name, …) и JSON-RPC 2.0
  (`apps.start|stop|install|status`; прочие namespace уходят в запущенное приложение);
  `"pose"` (unreliable, приходит вторым `ondatachannel` после `subscribe_pose`) — ~30 Hz,
  дропать `seq <= lastSeq`, команды туда не слать.
- `local_app` на роботе ≠ «нельзя подключиться»: сессия принимается как control-only.

## M8 — ReachyKit/ReachyMedia: удалённая сессия (транспорт)

- Seam сигналинга: протокол `SignalingTransport` — существующий WS :8443
  (`CameraSignalingClient`) и новый `CentralSignalingTransport` (M7) — RTC-половина не меняется
  (робот offerer, мы answerer, STUN-only), переиспользуется стек `ReachyMedia`.
- `Sources/ReachyKit/Central/RemoteControlChannel.swift` — канал `"data"`: JSON-команды
  (запрос/ответ `{"status":"ok"}` или payload-конверт) + JSON-RPC 2.0 (`apps.*`, id-корреляция,
  ошибки `reason`); канал `"pose"` — отдельный AsyncStream с dedup по `seq`.
- `RemoteRobotConnection` — конформит **те же capability-протоколы**, что `RobotConnection`,
  где поверхность есть удалённо: `RobotAPIClient` (wake/sleep/state/volume/robot-name через
  команды), `RobotAppsClient` (через `apps.*` JSON-RPC). **Не** конформит `WiFiConfigClient`,
  `DaemonUpdateClient` → существующие capability-флаги сами прячут недоступное (в этом смысл
  расслоения протоколов). `RobotSession.makeClient` уже инжектируем — remote = другая фабрика.
- Состояние стриминга: удалённо `state` приходит по `"pose"`-каналу → адаптер под интерфейс
  `StateStreamClient` для `ViewportModel`.
- Опасные команды (`restart_daemon`, `start_update`, `delete_hf_token`) удалённо в UI **не
  выносить**, пока не проверено гейтирование (зафиксировано как открытый вопрос).

Тесты: RPC-корреляция и ошибки, pose-dedup, маппинг протоколов на дублях; e2e — только ручное.

## Порядок и зависимости

M1 → M2 → M3 (независим от M1–M2) → M4 (нужен M1) → M5 (нужен M1) → M6 (нужны M2+M3) →
M7 (нужен M3) → M8 (нужны M7 + ReachyMedia) → M9 (нужны M6–M8) → M10. Каждый milestone
собирается/тестируется и коммитится отдельно; ветка публикуется целиком.

## Верификация

1. `./bin/mise run build` / `test` после каждого milestone (после правок тестов —
   `swift build --build-tests`, не `--skip-build`).
2. `./bin/mise run test:snapshots` → `record` для новых превью, явный `git add` PNG;
   генерирующую задачу — последней (16-pin `Package.resolved`).
3. `./bin/mise run build:app` — ReachySpike + ReachyWidgets.
4. `sim-daemon` + `test:sim` (за `REACHY_SIM_HOST`): `list-available` декодируется,
   `current-app-status` = nil, `job-status/unknown` = 404, `hf-auth/status` = logged-out.
   Реальную установку в интеграционных тестах не делать. `central-robot-status` на sim без
   токена → `reason: not_authenticated` — тоже проверить.
5. `GET https://pollen-robotics-reachy-mini-central.hf.space/health` — живой смоук central
   (без токена); контрактные тесты central — только на фикстурах (не бить боевой сервер из CI).
6. `./bin/mise run lint`, `format-check`.
7. Ручное на железе (PR-чеклист): install/запуск/стоп, вход в 1 кнопку (Safari залогинен/нет),
   привязка робота + появление в «Your Reachies», remote-сессия с мобильного интернета
   (и NAT-фейл → подсказка), эвикция локальным приложением, Local Network из widget-extension.

## Риски

- **NAT без TURN** — remote может не собраться (CGNAT/симметричный NAT); честный таймаут и
  подсказка. Продуктовое ограничение всего стека Pollen, не наше.
- Версионный скью демона: `no-evict`/device-flow только в main — не используем; `install_id`
  в meta может не приходить с 1.9.0 — ключ каскадный.
- WS job-стрима может молча висеть → `AppJobMonitor` всегда поллит параллельно; рестарт демона
  теряет job → отдельный исход + подтверждение по installed-списку.
- OAuth: client_id надо зарегистрировать руками (до этого — PAT); expiry без refresh_token →
  `needsReauth` (повторный вход почти мгновенен через куки Safari). Ротация токена = новый peer
  на central (кэш по строке токена).
- Rate limit central 1200/60 s → никакого агрессивного поллинга, SSE-дельты вместо refresh.
- Опасные remote-команды не выносим в UI до проверки гейтирования.
- PAT/токен по plain HTTP LAN при привязке — предупреждение в UI, тест «не в query».
- Local Network в widget-extension — подтверждается только устройством.
