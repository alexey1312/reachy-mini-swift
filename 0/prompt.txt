## 2. ReachyScene

- **`OrbitCamera`** (`OrbitCamera.swift:11`) holds the one aspect assumption, at `:69-79`:

  ```swift
  // Vertical field of view is 60° by default; 2.2 radii leaves a margin so
  // the robot does not touch the edges of the screen.
  distance = radius * 2.2
  ```

  Fixed 2.2× multiplier, never recomputed for the host's aspect. At the 160×112 window (1.43:1 landscape) the vertical FOV governs, so the robot is framed the same as full-screen with more slack sideways — it works, but nothing adapts.
- **Platform conditionals: none.** The only `#if` in the whole package is `#if DEBUG` at `RobotSceneModel.swift:176`. - **Hard constraint** (`Sources/ReachyScene/CLAUDE.md`): exactly **one live `RealityView` per `RobotSceneModel`**. An `Entity` has one parent, so a second view silently steals the robot. This is why the window and the tab are one identity, why `matchedGeometryEffect` is ruled out, and why `LiveTab` draws `Color.clear` when the window has the viewport (`LiveTab.swift:107`).

## 4. The gap your branch name points at

`FloatingViewportModifier.swift:43-49`:

```swift
private var hasTabBar: Bool {
    #if os(macOS)
        false
    #else
        horizontalSizeClass == .compact
    #endif
}
```

**On iPad (regular width) and on macOS the floating window does not exist at all.** `hasTabBar == false` collapses `placement` to `.inline` everywhere, `isStreaming` is permanently false, and `LiveTab` hides the "Mini window" toggle (`LiveTab.swift:51`). The stated reason (`Sources/ReachyUI/CLAUDE.md`, and `ReachyTabShell.swift:103`) is that `.tabViewStyle(.sidebarAdaptable)` draws a sidebar at regular width, so Live is permanently visible and there is nothing to float out of.

Everything downstream of that flag is already size-agnostic:
- `FloatingViewportModel` has no size-class knowledge; `hasTabBar` is a plain `var` written by one `onChange`.
- All geometry (`FloatingViewportGeometry.swift`) takes `size:` and `margin:` parameters defaulted to the metrics, and clamps for degenerate rectangles.
- `FloatingViewportPreviews.swift` already injects `hasTabBar: true` and records iPad-Pro-11 references for every window state (`:99` explicitly notes the iPad root captures show "the plain tab it is captured on").
- `FloatingViewportModelTests.regularWidthIsUnchanged()` (`:81`) is the test that pins the current behaviour.
