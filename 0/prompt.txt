## 1. Files to create, and why each lands where it does

### `Sources/ReachyWidgetUI/CallControlInbox.swift` — **cross-platform, no `#if`**

`CallControlInbox` (`@MainActor @Observable`, `static let shared`, monotonic `token: Int`, `Pending { control: CallControl, token: Int }`, `public func drop()`) plus `enum CallControl { case toggleMute, end }`.

Why here: it is the only thing both the intent (which must be in a target the appex links) and the drainer (`ReachyUI`) can see. It is pure Foundation + Observation — nothing ActivityKit — so keeping it out of the `#if` buys three things: `Tests/ReachyWidgetUITests` can test it under `swift test` on macOS, `RootCallLifecycle` needs no platform fork to drain it, and the macOS `ReachyWidgetUI` still compiles the type.

`drop()` is `public` here, unlike `CallRequestInbox.drop()`, because the drainer is in a different module.

**Do not reuse `CallRequestInbox`.** That mailbox carries a `robotID`, a TTL and `CallRequestRouting`'s robot-matching rule, none of which apply to "mute the call that is already up". Two mailboxes, two payloads.

### `Sources/ReachyWidgetUI/CallControlIntents.swift` — **whole file `#if os(iOS)`**

`CallMuteIntent` and `CallEndIntent`, both `LiveActivityIntent`, both `static let isDiscoverable = false`, both `@MainActor func perform()` posting one `CallControl` into `CallControlInbox.shared` and returning `.result()`. Names chosen to read as a family with the existing `CallRobotIntent`.

Why in `ReachyWidgetUI` and not the app target (where `CallRobotIntent` lives): the appex renders the `Button(intent:)`, so the appex must be able to *name* the type; the app must contain it to *run* it. Only `ReachyWidgetUI` is linked by both. The `CallRobotIntent` reasoning does not transfer — it is in the app target because `openAppWhenRun` errors in an appex, and these two set no such flag.

`ReachyShortcuts` needs no edit: neither intent carries an `AppShortcut` phrase, so the 10/10 ceiling is untouched.

Why here: `ActivityAttributes` must be identical in both processes, and this target is the one both link. Same placement rule as `RobotWidgetContent`.

### `Sources/ReachyUI/Navigation/CallLiveActivity.swift` — **cross-platform surface, `#if os(iOS)` bodies**

`@MainActor enum CallLiveActivity` with three statics: `start(robotName:isMuted:)`, `update(isMuted:) async`, `end() async`.

`start` must swallow its throw and log: `ActivityAuthorizationInfo().areActivitiesEnabled` is a per-app user toggle, and a user who turned Live Activities off must not lose the call over its garnish — the same reasoning `CallLifecycle` records for `startFailed`.

## 2. How Mute/End reach `RobotCallController` without `ReachyWidgetUI` seeing `ReachyMedia`

Concrete chain, five named types:

1. **`CallMuteIntent` / `CallEndIntent`** (`ReachyWidgetUI`, `LiveActivityIntent`) — run in the app's process, know nothing about calls.
2. **`CallControlInbox.shared`** (`ReachyWidgetUI`, `@MainActor @Observable`) — `receive(.toggleMute)` / `receive(.end)` bumps a token and publishes `Pending`.
3. **`RootCallLifecycle`** (`ReachyUI/Navigation`) — the only place linking both sides; observes `inbox.pending?.token`.
4. **`RobotCallController.endCall()` / `.toggleMic(for:)`** (`ReachyMedia`) — the existing methods.
5. **`CallLifecycle`** — emits `EndConversationAction` / `MuteConversationAction`.

The dependency arrow never reverses: `ReachyUI → ReachyWidgetUI` (already declared), and `ReachyWidgetUI` gains nothing. The mailbox is the seam, and it is the *same* seam `CallRobotIntent → CallRequestInbox → RootCallLifecycle` already uses — one more instance of an established pattern, not a new mechanism.

Load-bearing: the End goes through `call.endCall()`, never at `CameraSession` directly, so the Live Activity's End, the Lock Screen's End and `CameraViewport`'s `CallEndButton` stay one `EndConversationAction` funnel. That invariant is the whole point of `Sources/ReachyMedia/AGENTS.md:64-71`.

## 4. The macOS story

ActivityKit is not available on native macOS, and `LiveActivityIntent` is not either. Since the app's `.mac` destination is native macOS (not Catalyst), `#if os(iOS)` is the correct fork and `#if canImport(ActivityKit)` is not — it would go true under Catalyst and mislead the next reader. This matches the repo's existing precedent, which is deliberately a *deployment-target* fork for `ControlWidget` and a *platform* fork for LiveCommunicationKit; this one is platform, like LiveCommunicationKit, and no macOS floor bump brings it back.

**Whole-file `#if os(iOS)`:**
- `Sources/ReachyWidgetUI/CallControlIntents.swift`
- `Sources/ReachyWidgetUI/CallActivityAttributes.swift`
- `Sources/ReachyWidgetUI/CallActivityView.swift`
- `Apps/ReachyWidget/Sources/RobotCallActivity.swift`

**Cross-platform, no fork:**
- `Sources/ReachyWidgetUI/CallControlInbox.swift` — pure Foundation/Observation. Keeping it out of the fork is what lets `Tests/ReachyWidgetUITests` run it under `swift test` on the macOS host, and lets `RootCallLifecycle` drain without an `#if`.
- `Sources/ReachyUI/Navigation/CallLiveActivity.swift` — cross-platform type, `#if os(iOS)` inside each body; on macOS all three are no-ops, exactly like `RobotCallController.endCall`.
- `Sources/ReachyUI/Navigation/RootCallLifecycle.swift` — no fork. On macOS `call.activeCall` is permanently nil, so the trigger never fires a start and the drain never has a call to act on. Inert rather than absent, which is what the file already does for previews.
- `Apps/Project.swift` — one plist, and macOS ignores the key.

**`ReachyWidgetBundle.swift`** — `activities` goes inside the existing `#if os(iOS)` branch; the `#else` branch (`readings` only) is untouched, so the Mac widget gallery is unchanged.

**`check-appintents-metadata.sh` macOS pass:** stays green because the two iOS-only intents are in `IOS_ONLY_APP_ACTIONS` and the macOS bundle is detected by `Contents/MacOS`. Without that split, adding them to `REQUIRED_APP_ACTIONS` would fail `Scripts/release-macos.sh` on every archive — the exact trap `CallRobotIntent`'s doc comment already records ("an `#if os(iOS)` here would fail the macOS release build").

**Build coverage gap to know about:** `swift build` / `mise run build` compiles the package for the macOS host only, so it proves the `#if` did not break macOS and proves *nothing* about the iOS branch. The first real compile of the new code is `mise run build:app:ios`. Sequence the work accordingly (§6).

## 7. What I think you have got wrong or are missing

**a. "Lock Screen only" is not a shippable option.** As above — `dynamicIsland:` is a required closure. The island code gets written either way; only its ambition is at stake.

**b. `NSSupportsLiveActivities` is not the only silent off-switch.** `ActivityAuthorizationInfo().areActivitiesEnabled` is a per-app user toggle (Settings → Hey Reachy → Live Activities), and `Activity.request` throws when it is off. `start()` must log and continue, never propagate. The repo already has the sentence for this: the framing is garnish, the microphone is the meal.

**c. "A Live Activity's own process has no network access" is true but not the constraint you'll trip on.** The rendering happens in `ReachyWidget.appex`, which *does* have `com.apple.security.network.client` (added for the interactive widget buttons). Nothing here needs it: the card renders entirely from `ContentState`, pushed by the app. Say so in the file header, or someone will reach for `RobotSnapshotStore` and add an App Group read that cannot be correct — the app is right there and already knows.

**d. You have no zombie-activity story, and you will hit it.** Kill the app mid-call and the Lock Screen keeps a card with two live buttons and no call behind them. The stateless `CallLiveActivity` design handles it: `start` sweeps `Activity&lt;RobotCallAttributes&gt;.activities` before requesting. Also end with `dismissalPolicy: .immediate` — the default leaves the card up for hours after hangup, which for a call reads as a bug.

**e. Skip `staleDate`.** It is the wrong tool: it greys the card rather than removing it, and it would have to be re-armed on every update. The stray sweep plus `.immediate` covers the same ground with less machinery.

**f. Two mute truths, and the card will lag by a round trip.** `CameraSession.isMicEnabled` is the mic; `MuteConversationAction` is the system's. `CallLifecycle` keeps them in step, but between `performMuteAction` and `performedMute` the track has not flipped. Read `isMicEnabled` for the card and accept the lag. Do not add a third `isMuted` to `RobotCallController` to smooth it — that is a new truth to keep in step with two others.

**g. Watch the trigger source: `activeCall`, not `keepsSessionAlive`.** `keepsSessionAlive` is true from the tap that asks for the microphone, before the system hands the start back and before `robotName` exists. Starting an activity there produces a card naming nobody, then a second card when the real one starts. `RobotCallController` already documents this exact distinction for the viewport gate.

**h. Both intents in `ReachyWidgetUI` means both are extracted into the appex's metadata too.** Harmless — the check script asserts a minimum, not an exact set, and `isDiscoverable = false` keeps them out of Shortcuts. But it is the one thing to look at first if a button on device does nothing: read the *app* bundle's `extract.actionsdata` and confirm both are there with `isDiscoverable: false`, using the `python3 -c` one-liner in `Sources/ReachyWidgetUI/AGENTS.md`.

**i. `CallEndButton` already exists** in `Sources/ReachyUI/CameraViewport.swift`. Different module so it compiles, but name the new ones `CallActivityEndButton` / `CallActivityMuteButton`.

**j. `check-catalogue.py` does not respect `#if`.** It strips comments and scans source text, so the iOS-only strings are checked like any other and `mise run lint` fails until de/es/fr/ru are all filled. This is not a problem, just a gate that will surprise you at step 6 if you expected the fork to hide them. Reuse the existing `"End call"` key from `CameraViewport` rather than minting a second.

**k. Do not draw call duration on the card.** `Text(_:style: .timer)` is the natural thing to reach for and it makes the reference images churn — it renders live in a real activity and as a frozen arbitrary string in a snapshot. The system's own call pill already shows duration.
