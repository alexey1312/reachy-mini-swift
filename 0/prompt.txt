## 4. Main screen on iPad/Mac, and the wasted width

On iPad/Mac `.sidebarAdaptable` renders a sidebar with the five destinations; the selected tab's content fills the full detail area. Default tab is `.robot` (`ReachyRouter.init(tab: .robot)`, `ReachyRootView.swift:62`) → `RobotScreen`, a bare `Form` (`RobotScreen.swift:25`).

**No tab content is width-constrained.** The only `Metrics.readableForm` (560 pt) call site in the entire repo is the *gate*: `ConnectGate.swift:31–32`. The comment there names the exact problem it solves — "A `Form` left to itself fills a 1024 pt iPad, and rows a metre wide with three words in them read as a broken layout. Nothing constrained this before because the tab bar's column did." That constraint was never extended to the shell.

So on iPad/Mac:
- `RobotScreen` (`Form`), `SettingsScreen` (`Form` + `.formStyle(.grouped)`, `Settings/SettingsScreen.swift:31–43`), `MovesScreen`, `AppStoreScreen` all stretch to the full detail width.
- The only in-tab width caps are content-local and small: `LiveTab.swift:115` (`.frame(maxWidth: 420)` on `AsleepBanner`), `ControllerScreen.swift:62` (280), `ViewportView.swift:174` (240) / `:219` (220).
- `Metrics.window` doc (`Metrics.swift:74–89`) explicitly assumes "every screen here is a column of cards capped at `readableForm`, so height is what they need and width past the cap is only margin" — which is true of the gate and *not* true of the shell. That is the gap.

Snapshot coverage does exist for the sidebar layout: `Apps/.prefire.yml:16–19` captures `iPhone 16 Pro` **and** `iPad Pro 11`; `Sources/ReachyUI/Previews/ReachyRootViewPreviews.swift:9` notes "The iPad shots are the ones carrying `.sidebarAdaptable`".

## Notes for whoever changes this

- The five tabs being unconditional is load-bearing for `.sidebarAdaptable` (`ReachyTabShell.swift:8–12`, `ReachyRouter.swift:7–11`); a conditional tab breaks sidebar adaptation and forces selection-dragging.
