## 1. Known-robots storage shape

**`/Users/aleksei/Developer/reachy-mini-desktop-app-swift/.claude/worktrees/available-issues-review-0ce72a/Sources/ReachyKit/Model/KnownRobot.swift`** holds both `KnownRobot` (L8-24) and `KnownRobotStore` (L31-89).

Keys and format (`KnownRobot.swift:32-33`, 42-61, 85-88):

```swift
static let knownRobotsKey = "ReachyKit.knownRobots"
static let lastAddressKey = "ReachyKit.lastAddress"
...
public var all: [KnownRobot] {
    guard let data = defaults.data(forKey: Self.knownRobotsKey),
          let robots = try? JSONCodec.stored.decode([KnownRobot].self, from: data)
    else { return [] }
    return robots.sorted { $0.lastConnected &gt; $1.lastConnected }
}
```

- Both values are **`Data` blobs of JSON via `JSONCodec.stored`** — `[KnownRobot]` under `knownRobotsKey`, a single `RobotAddress` under `lastAddressKey`. Never a plist/dictionary. KVS accepts `Data`, so the shape carries over unchanged.
- `KnownRobot` = `{key, name?, address, lastConnected}`, `key` is `RobotIdentity.deduplicationKey` (hardware ID). `RobotAddress` = `{host, port}` (`Sources/ReachyKit/Model/RobotAddress.swift:4-13`, default port 8000).
- `JSONCodec.stored` is **frozen** — `Sources/ReachyJSON/JSONCodec.swift:28-35` says changing it makes shipped records undecodable, and every store reports that as empty rather than an error. A KVS mirror must reuse `.stored` verbatim; no re-encoding.
- Sort is on read, not on disk. `remember` upserts by `key`; `forget` also clears `lastAddress` when it pointed at the removed robot (`KnownRobot.swift:76-83`) — that side effect matters for a merge policy (a delete on device A must not be resurrected by device B's copy).
- `lastAddress` is *not* per-robot: it is "the address to offer first" — the manual field's prefill and the first candidate the sweep tries (`KnownRobots.swift:84-87`, `Sources/ReachyUI/Connect/CandidateSweep.swift:96`, `Sources/ReachyUI/ConnectionScreen.swift:75`). It is device-local by nature: a LAN IP that is meaningless on another network. Strong candidate for **not** syncing.

**Store resolution / injection** — `Sources/ReachyKit/Model/KnownRobots.swift:65-75`:

```swift
public nonisolated(unsafe) static let defaults: UserDefaults = {
    guard let group = appGroupIdentifier,
          let shared = UserDefaults(suiteName: group)
    else { return .standard }
    migrate(from: .standard, to: shared)
    return shared
}()

public static var store: KnownRobotStore {
    KnownRobotStore(defaults: defaults)
}
```

`appGroupIdentifier` (L48-50) reads the Info.plist key `ReachyAppGroupIdentifier`; absent (fork, unit test) → `.standard`. `KnownRobots.all/lastAddress/remember/forget` are thin statics over `store` — that is the "already resolves its store" the issue refers to. Note `store` is a **computed property returning a fresh value struct each access**, so there is no single instance to hang an observer on.

Migration precedent worth copying for a KVS pull: `migrate(from:to:)` (L29-36) is a once-only, key-by-key copy guarded by `ReachyKit.migratedToAppGroup`, over the ordered list `persistedKeys` (L15-20 = knownRobots, lastAddress, onboarding, provisioned).

## 3. Entitlements pattern (`Apps/Project.swift`)

Group name is one constant at the top, `Apps/Project.swift:6`: `let appGroup = "group.com.alexey1312.ReachyMini"`, referenced into both targets' Info.plists at `:125` (app) and `:211` (widget) as `"ReachyAppGroupIdentifier": .string(appGroup)`.

Entitlements are **hand-written plist files selected per SDK in build settings**, not generated by Tuist:

```swift

settings: .settings(base: [
    "SWIFT_VERSION": "6.0",
    "CODE_SIGN_ENTITLEMENTS": "ReachyMini/Entitlements/ReachyMini-iOS.entitlements",
    "CODE_SIGN_ENTITLEMENTS[sdk=macosx*]": "ReachyMini/Entitlements/ReachyMini-macOS.entitlements",
```

```swift
// widget target, Apps/Project.swift:245-249
"CODE_SIGN_ENTITLEMENTS": "ReachyWidget/Entitlements/ReachyWidget-iOS.entitlements",
"CODE_SIGN_ENTITLEMENTS[sdk=macosx*]":
    "ReachyWidget/Entitlements/ReachyWidget-macOS.entitlements",
```

Four files, all four already carrying `com.apple.security.application-groups` with the literal group string:
- `Apps/ReachyMini/Entitlements/ReachyMini-iOS.entitlements` (10 lines, groups only)
- `Apps/ReachyMini/Entitlements/ReachyMini-macOS.entitlements` (sandbox, groups, audio-input, bluetooth, network client+server)
- `Apps/ReachyWidget/Entitlements/ReachyWidget-iOS.entitlements` (groups only)
- `Apps/ReachyWidget/Entitlements/ReachyWidget-macOS.entitlements` (sandbox, groups, network.client)

So adding `com.apple.developer.ubiquity-kvstore-identifier` is **two files** (`ReachyMini-iOS`, `ReachyMini-macOS`) under the stated design. The split reason is documented at `Apps/Project.swift:174-177` and in the widget macOS plist's own comment: macOS-only keys fail an iOS build against any profile — an iCloud key is not macOS-only, so it goes in both app files with the same value. Note the group identifier is hard-coded as a literal in the plists while `Apps/Project.swift:6` holds the Swift constant — the same duplication already exists, so a KVS identifier will be a literal too (typically `$(TeamIdentifierPrefix)$(CFBundleIdentifier)`, but the team prefix is nowhere in this repo today — no `DEVELOPMENT_TEAM` in `Apps/Project.swift`, worth checking signing config before writing a literal).

Widget: it reads `KnownRobots.all` and `ThemeStore` from the app-group suite in its own process (`Sources/ReachyWidgetUI/RobotEntity.swift:74`, `RobotPowerIntents.swift:65`, both widget views above). If the app mirrors KVS↔UserDefaults, the widget needs no entitlement and no change. Adding the KVS entitlement to the extension would also require the same store identifier and a second observer in a process that is woken briefly — not worth it.

## 5. Onboarding flags — how they are used

Both live in the same suite and are already in `persistedKeys` (`KnownRobots.swift:15-20`), so an unthinking "sync everything in persistedKeys" would sweep them in.

- `hasCompletedOnboarding` (`KnownRobots.swift:99-102`, key `"ReachyKit.hasCompletedOnboarding"`). Written at `Sources/ReachyUI/Onboarding/OnboardingModel.swift:228,236`; read once at `Sources/ReachyUI/ConnectionScreen.swift:299` — `if KnownRobots.lastAddress == nil, !KnownRobots.hasCompletedOnboarding` → auto-open onboarding. Its own doc says it "only stops onboarding from opening itself a second time — the flow is never a gate". Arguable either way: syncing it spares a second device the auto-open; leaving it local means a new device offers the setup flow, which for a BLE Wi-Fi provisioning flow performed *from that device* is probably the right behaviour.
- `pendingProvisionedHardwareID` (`KnownRobots.swift:110-119`, key `"ReachyKit.pendingProvisionedHardwareID"`). Written by `OnboardingModel.swift:227` right after a BLE Wi-Fi handover, cleared on the matching handshake at `Sources/ReachyKit/Session/RobotSession+Connect.swift:100-101`. Read once at `ConnectionScreen.swift:76` into `@State` at init — and `Sources/ReachyUI/CLAUDE.md` records that this specific read is why the property is assigned in `init` rather than as a default: the value is cleared by the handshake, so a deferred read is a banner that never appears. This is a **short-lived hand-off token for a provisioning session on one device**; syncing it would make another device display "waiting for a robot to come back on the network" for a robot it never provisioned. Clear candidate for staying local.

Also local by nature and in the same suite: `KnownRobots.migratedToAppGroup` (must never sync — it is a per-container marker), `lastAddress` (LAN-specific), and the widget/snapshot caches (`RobotSnapshotStore`, `RobotAppsCacheStore`, `PinnedAppStore`, `MovePlaybackRecord`, `MoveRecording`, `RobotAppLaunchState`, `RobotPowerTransitionState` — all `UserDefaults = KnownRobots.defaults`, all robot-session state).

## Loose ends a planner should decide

- `KnownRobots.store` is a computed property returning a fresh struct; there is no instance to attach a KVS observer to. The mirror will most likely be a separate type writing into `KnownRobots.defaults` under the same two keys, leaving `KnownRobotStore` untouched — which keeps `.stored` frozen and every existing test valid.
- Merge semantics: `[KnownRobot]` is keyed by `key` with a `lastConnected` date, so a last-writer-wins union on `key` by `lastConnected` is natural — but it cannot represent a deletion (`forget` just drops the element), so a naive union resurrects forgotten robots. Same trap `migrate(from:to:)` documents at `KnownRobots.swift:25-28`.
- KVS limits (1 MB total, 1024 keys) are not a concern for two small values; nothing here approaches them, unlike the multi-MB `RobotCatalogueCache` which is files in the group container, not defaults.
- Tests will need a seam: `NSUbiquitousKeyValueStore` has no suite equivalent, so injecting a protocol with a `UserDefaults`-backed fake is the only way to keep the existing per-test-suite pattern (`swift test --parallel` is why every store here is injectable).</result>
