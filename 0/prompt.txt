### 1. `RemotePoseStream` — `Sources/ReachyKit/Central/RemotePoseStream.swift`
**Verdict: the one type here that needs changes before merge.** Correct in the happy path, but its lifecycle invariant ("at most one reader, and it owns the subscription") is maintained by convention across three methods rather than by construction, and `@unchecked Sendable` is doing real work.

Problems:

- **`RemotePoseStream.swift:70` — the reader `Task` captures `self` strongly.** The capture list `[connection, channel]` is undone by `self.broadcast(...)` at `:96` and `self.finishAll()` at `:101`. Task → self → `reader` → Task is a retain cycle for as long as the channel is open, so `deinit` at `:33` can never run while a reader exists. That `deinit { reader?.cancel() }` is dead code, and it also reads `reader` outside the lock — the only unsynchronised access in the file. Use `[weak self]` at `:70` and the cycle and the unsafe read both go.
- **`:59-64` / `:68` — subscribe/unsubscribe can invert.** `remove` sets `reader = nil` and cancels; the cancelled task's `defer { Task { try? await connection.unsubscribeFromPose() } }` (`:75`) is *detached* and unordered. A new subscriber arriving in that window passes the `reader == nil` guard, sends `subscribe_pose`, and then the old task's `unsubscribe_pose` lands on top of it — the new subscriber gets a stream that never yields. `deinit`/cancel ordering is not enough here; the unsubscribe needs to be sequenced against the next subscribe (a single serialising actor, or an `await` on the retiring task before a restart).
- **`:68-70` — a completed reader is not distinguishable from a live one.** If the channel closes while nobody is subscribed, `finishAll()` runs, no `onTermination` fires (no subscribers), and `reader` stays non-nil forever. The next `updates(_:)` returns a stream that never yields and never finishes. `reader == nil` is the wrong predicate for "no one is reading".
- **`:91` — a stale frame increments `diagnostics.unsupportedFrames`.** Out-of-order is neither unsupported nor a decode failure; it will read as daemon incompatibility in the health screen. Either add a counter or reuse none.
- `@unchecked Sendable` at `:21` is honest about the mechanism (NSLock over both mutable fields) but not enforced by the type — an actor holding the subscriber table, with the reader as a child task, would remove `@unchecked`, the manual `startReadingLocked` naming convention, and both races above. That is the recommendation, not a nice-to-have.

Encapsulation 6/10 · Invariant expression 4/10 · Usefulness 9/10 (the fan-out is genuinely needed — `messages()` really is single-consumer)

### 2. `MovePlaybackClient` + `RemoteRobotConnection`'s playback half — `Sources/ReachyKit/Session/MovePlaybackClient.swift`, `Sources/ReachyKit/Central/RemoteRobotConnection.swift:187-241`
**Verdict: the protocol split is right; the capability model on it is now three-valued and the relay's move UUIDs are counterfeit.**

Problems:

- **Three different ways to say "I can't", and callers use all three.** Not conforming (`ReachyKitError.movesUnavailable` via `withMovesClient`), `offersMoveLibrary == false` (simulator), and a thrown `URLError(.unsupportedURL)` from the extension defaults (`MovePlaybackClient.swift:57-81`). The project's stated convention is "conforming *is* the capability" (`Sources/ReachyKit/AGENTS.md:198-199`); this type keeps the throwing defaults *and* adds a flag. Result: `RobotSession+Moves.swift:31` has to detect "this transport cannot list moves" by **catching a URLError code** — `catch let error as URLError where error.code == .unsupportedURL` — which is capability detection through an error value. Any unrelated `.unsupportedURL` (a malformed URL built inside `RobotConnection`) silently serves a week-old disk cache instead of surfacing.
- **`offersMoveLibrary` answers two questions with one bool.** Its doc (`MovePlaybackClient.swift:23-26`) concedes it: the relay "conforms with no index route and answers true anyway". So the flag means "offer the moves screen", not "has a library". Split it (`offersMoveLibrary` for the index, conformance for playback) and the `URLError` catch above becomes `guard client.offersMoveLibrary`.
- **`playMove`/`gotoNeutral` mint UUIDs that identify nothing** (`RemoteRobotConnection.swift:202-203`, `:240-241`). `stopMove(uuid _:)` at `:226` ignores its argument, and `gotoNeutral` overwrites a live play's handle. The type's contract — "a UUID identifies one move task" — is false on this transport, and the only thing preventing a bug is that `RobotSession` happens to keep one activity at a time. If the handle cannot identify anything, the protocol should say so: `func playMove(...) async throws -&gt; MoveHandle` where `MoveHandle` is `case daemon(String)` / `case opaque` would make the relay's limitation checkable rather than papered over with a `UUID()`.
- `runningMoveUUIDs()` at `:210-220` answers "*some* move is running" as "*your* move is running". A dance started from another client keeps a finished handle alive indefinitely. Documented at `:206-208`, but the doc is the enforcement.

Encapsulation 7/10 · Invariant expression 4/10 · Usefulness 8/10

### 3. `Envelope` — `Sources/ReachyKit/Central/RemoteControlChannelEnvelope.swift`
**Verdict: a bag of optionals where the domain is a sum type.** Six independent fields encode four mutually exclusive frame kinds, and the discrimination is re-derived by hand in `RemoteControlChannel.deliver` (`:315-340`).

Problems:

- `isRPC`/`rpcID`/`method` at `:17-19` carry an unexpressed invariant: `isRPC` implies exactly one of `rpcID` or `method`. Nothing enforces it, and the failure is silent — an RPC frame whose `id` is a JSON *string* (legal per JSON-RPC 2.0) decodes as `isRPC = true, rpcID = nil, method = nil` and is dropped at `RemoteControlChannel.swift:322-329`, leaving the caller to time out with no diagnostic. A computed `var route: Route` (`.rpcReply(Int)` / `.rpcNotification(String)` / `.typed(String)` / `.command(String)` / `.keyed(Set&lt;String&gt;)`) puts the whole routing decision in the type and lets `deliver` be a single switch.
- `:24-28` — four `try?` swallow every decode error. Given `AnyKey` and `decodeIfPresent` these can only fail on a type mismatch, which is exactly the string-`id` case above. Worth at least not being invisible.
- Moving the type from `private` (nested in `RemoteControlChannel`) to **module-internal file scope under the bare name `Envelope`** widens it more than the stated reason (file length) requires. `RemoteControlChannel.Envelope` in an extension would have kept the namespace.

### 5. `RobotUnlinkClient` / `RobotRenameClient` — `Sources/ReachyKit/Session/HFAuthClient.swift:15-24`, `Sources/ReachyKit/Session/RobotRenameClient.swift:11`
**Verdict: two capability protocols in one PR, using two opposite idioms, and one of them is unsound.**

- **`RobotUnlinkClient` has a throwing default (`HFAuthClient.swift:19-23`) *and* is used as a conformance test**: `RobotSession+HFAuth.swift:17-18` is `client is any RobotUnlinkClient`. ## Critical gaps (8–10)

**1. The relay's entire move-playback surface has no test.** `Sources/ReachyKit/Central/RemoteRobotConnection.swift:193–243`
`preload`, `playMove`, `runningMoveUUIDs`, `stopMove`, `gotoNeutral` — the whole of commit `c85558e6` — are exercised nowhere. `runningMoveUUIDs` (line 210) is genuinely stateful: it mints a local handle, reads `is_move_running`, and clears the handle on a false. Delete the `if !running { self.playbackHandle = nil }` and a finished dance never leaves the "playing" phase; invert `guard let playbackHandle else { return [] }` and it crashes. Nothing goes red. The one test that touches this area (`RemoteRobotConnectionTests.swift:290`) only asserts that `listMoves` *throws*.
*Rating 9.* Add a `FakeDataChannel` suite: play → handle non-empty; `is_move_running:false` → empty set and the handle cleared; `stopMove` clears it and sends `stop_move`; `playMove` puts `move_name`/`dataset_name` on the wire.

**2. `RemoteControlChannel.call` id uniqueness and non-serialisation are unproven.** `Sources/ReachyKit/Central/RemoteControlChannel+RPC.swift:21`, `RemoteControlChannel.swift:156`
The doc states the design guarantee outright: "an id is unique per call, so two calls are never each other's reply… `apps.install` runs for minutes and a status poll must not queue behind it." Both tests (`matchesRPCByID`, `throwsRPCErrorWithReason`) issue a **single** call and hard-code `"id":1`. Make `nextRPCID()` return a constant and both still pass — while two concurrent calls would then cross-match replies, silently returning an install's result to a status poll.
*Rating 9.* Two concurrent `call`s, answer the second's id first, assert each got its own payload — and that the first is not blocked.

**3. The RPC-first ordering in `deliver` has no test.** `Sources/ReachyKit/Central/RemoteControlChannel.swift:318`
The comment names the exact bug the branch placement prevents: RPC keys "`jsonrpc`, `result`, `id` — would otherwise fall to the key match below and answer whichever waiter happened to be tokened `result`." Move the `if envelope.isRPC` block below the key match and every test still passes.
*Rating 8.* One test: a pending `perform(correlation: .replyKey("result"))` must not be satisfied by an inbound JSON-RPC frame.

**4. `canManageApps`'s semantic change is invisible to the suite.** `Sources/ReachyKit/Session/RobotSession+Apps.swift:13`
Changed from `client is any RobotAppsClient` to `offersAppStore == true`. Every apps double in the repo (`AppsRobotClient`, `AppLifecycleClient`, `AppsCapablePreviewClient` in `Tests/ReachyUITests/RunningAppModelTests.swift:6`) takes the protocol default `offersAppStore == true`, and every "no store" test uses a client that is not a `RobotAppsClient` at all. Revert the line and nothing fails — but the relay would offer an App Store whose catalogue, installs and removals all throw.
*Rating 8.* A session-level double conforming to `RobotAppsClient` with `offersAppStore == false`, asserting `canManageApps == false`.

**5. The `canManageApps` / `canControlRunningApp` split is never exercised.** `Sources/ReachyKit/Session/RobotSession+Apps.swift:22`, `Sources/ReachyUI/Apps/RunningAppModel.swift:306`
Same root cause as (4): no test builds a session where the two flags disagree, which is exactly the relay case and the entire point of commit `885169ac`. `skipsRefreshWithoutTheCapability` (`RunningAppModelTests.swift:274`) uses a bare `RobotSession()` with no client, so it proves only that a disconnected session is not polled. Swap `canControlRunningApp` back to `canManageApps` in `canPoll` and the suite is green, while the dock stops watching the running app over the relay.
*Rating 8.*

**6. `supportsRename` over the relay is untested and uncaptured.** `Sources/ReachyKit/Session/RobotSession+Connect.swift:96`
`supportsRename = handshake.supportsRename || client is any RobotRenameClient` — the `||` clause has no test. `RobotSessionRenameTests` only drives `Handshake.supportsRename`, and the relay's own handshake still returns `false` (`RemoteRobotConnection.swift:57`), so the clause is the *only* thing making the field editable. Delete it and renaming silently greys out over the relay.
*Rating 8.* Also uncaptured: `PreviewRemoteRobotClient` does not conform to `RobotRenameClient`, and `RobotSession.preview` defaults `supportsRename: true` (`PreviewFixtures.swift:310`), so the relay settings reference would look identical either way.

## Important improvements (5–7)

**7. `RemoteRobotConnection.imuReading()` / `stateFrame()` / `deleteHFToken()`.** `RemoteRobotConnection.swift:256, 279, 293`
`matchesByReplyType` proves the channel routes `imu_data`, but nothing proves the reply is mapped into a `RobotIMUReading` with the right fields. `stateFrame()` has a real nil-guard (line 285) and a nested-4×4 flattening that duplicates `RemoteStateSnapshot.frame` — despite that type's doc claiming "the translation, in one place rather than two". Neither the nil case nor the flattening is asserted. `deleteHFToken` over the relay is covered only by a hand-rolled `RelayClient` double, never by the real connection. *Rating 7.*

**8. `RemoteControlChannel.call` has no timeout test.** `RemoteControlChannel.swift:163`
`perform` has three (`expectTimeout`, lines 87/97/108); `call` has none, and the `timeout: Duration?` override is dead in tests. This is precisely rule 7's "the duration is the assertion" shape and the helper already exists. *Rating 6.*

**9. `throwIfRPCError`'s other two branches.** `RemoteControlChannel+RPC.swift:89–94`
Only the with-reason path is tested. An error with no `data.reason` and an error with no `message` (the `"The robot refused the call"` fallback) are both untested — and the second is the string a user reads. *Rating 5.*

**10. `waitForMoveToFinish`'s new early return.** `Sources/ReachyKit/Session/RobotSession+Power.swift:208–209`
`guard let client = client as? any MovePlaybackClient else { return }` replaced the old guarantee that `RemoteRobotConnection.runningMoveUUIDs() -&gt; []` gave. There is no test of this function at all — remove the guard and wake/sleep silently stall for the full budget on any non-playback transport. *Rating 6, and it is the textbook rule-7 case: measure a `ContinuousClock` span.*

**11. `ViewportModel`'s relay wiring.** `Sources/ReachyUI/ViewportModel+Remote.swift:36, 50, 62`
- `remotePose` picks pushed-vs-polled off `camera.poseChannel.isOpen` — untested in both directions.

Remove the memo and the scene and the hearing indicator each open a reader, the second stealing the first's frames. `RemotePoseStreamTests.fansOutToEverySubscriber` tests the stream's fan-out, not the model's sharing of it, so it would not catch this.
- `startRemoteHearing`'s `hearing == nil, poseChannel.isOpen` guard, and `detach()` clearing `poseStream` (`ViewportModel.swift:170`), are untested.
*Rating 7 for the memo, 5 for the rest.*

**12. `PresenceModel.watchFace`'s weight-commit guard.** `Sources/ReachyUI/PresenceModel.swift:111`
`if isTracking, faceWatch != nil { return }` exists solely so a slider commit does not blank the line — the comment says so. Neither new test commits a weight while tracking. Delete the guard and "Following someone" flickers to nothing on every slider release. *Rating 6.*

**13. `AppStoreModel`'s forced refresh.** `Sources/ReachyUI/Apps/AppStoreModel.swift:266`
`session.appUpdates(force: refresh)` is the whole of commit `cd7922ba`. `StoreRobotClient.appUpdates(force _: Bool)` ignores the flag, so no test records it. Revert to `force: false` and the pull-to-refresh gesture silently returns the daemon's cache. *Rating 6.*

**14. `RobotConnection.imuReading()` swallows every failure as "no IMU".** `Sources/ReachyKit/Transport/RobotConnection.swift:299`
`guard let payload = try? await client.getImuApiStateImuGet().ok.body.json else { return nil }` — the doc claims "a decoding failure here is that null and nothing else", but `try?` also eats a timeout, a 500, and an `.ok` mismatch. **16. `WiFiJoinModel.canSend`'s phase guard.** `Sources/ReachyUI/Settings/WiFiJoinModel.swift:58`

Telling a user to power-cycle a robot in the middle of a `pip install` is actively harmful advice, and it directly contradicts this file's own rule at line 168-170 (*"A cancelled call leaves the state exactly as it was"*), which `fail(on:)` honours and this path bypasses. Both exits need to be distinguished from "the daemon went away": budget exhaustion deserves its own state ("still installing — check back"), cancellation deserves no state change at all.

### 10. Face-tracking poll fails forever, unlogged and unreported

### 12. Pre-release toggle stays live on a robot known to refuse pre-releases

### 13. Relay with no cached move index shows "unsupported URL"

### 14. Malformed channel frames are dropped silently, costing the caller a full timeout
`Sources/ReachyKit/Central/RemoteControlChannel.swift:314`

```swift
guard let envelope = try? JSONCodec.daemon.decode(Envelope.self, from: data) else { return }
```

`Envelope.init` uses `try?` on every field (`RemoteControlChannelEnvelope.swift:24-28`), so this only fails for a frame that is not a JSON object at all — but when it does, the frame vanishes with no counter and no log, and the waiting caller sits out its whole 10 s (or 30 s opening) budget and reports `.timedOut`, which reads as "the robot went quiet" rather than "this client could not read what it sent". `RemotePoseStream` at least counts these (`diagnostics.decodeFailures`); the control channel counts nothing.

The new JSON-RPC branch (line 318-329) adds a second drop: `rpcID` is decoded as `Int`, and JSON-RPC permits string ids. An id echoed as a string falls through to `envelope.method` (nil on a response) and the frame is discarded — again as a silent full-budget timeout.

### 15. `Cancel` during `.sending` discards the outcome of a join in flight
`Sources/ReachyUI/Settings/WiFiSettingsCard.swift:86-94` + `WiFiJoinSheet.swift:91-93`

The toolbar Cancel sets `joining = false` unconditionally, including while `model.phase == .sending`. The send was launched from a button action (`Task { await model.send(session: session) }`), not from `.task`, so it is not cancelled — it completes against a model nobody is watching. The user is left with no idea whether the robot took the network, and the robot may well be switching. Disable Cancel while `.sending`, or keep the sheet up until the phase resolves.
