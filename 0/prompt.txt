## 4. The connected robot's identity at root level

`RobotSession.phase` is the holder: `Sources/ReachyKit/Session/RobotSession.swift:10–15`
```swift
public enum ConnectionPhase: Equatable, Sendable {
    case idle
    case connecting(ConnectionStep)
    case connected(RobotIdentity)
    case unreachable(RobotIdentity)
}
```
`RobotIdentity` (`Sources/ReachyKit/Model/RobotIdentity.swift`) is `Hashable, Sendable, **Codable**` with `hardwareID: String?`, `name: String?`, `daemonVersion: String?`, and `deduplicationKey: String { hardwareID ?? name ?? "unknown" }` (`:23–25`). Explicitly identity-not-address (doc comment `:5–6`, upstream #269).

The existing precedent for reading it at root level is `RootLifecycle.swift:136–141`:
```swift
private var connectedRobotID: String? {
    switch session.phase {
    case let .connected(identity), let .unreachable(identity): identity.deduplicationKey
    case .idle, .connecting: nil
    }
}
```
That is exactly the shape a Handoff payload should carry (`deduplicationKey`, or the full `Codable` `RobotIdentity`). `session.link` (`RobotSession.swift:24–38`) is `.none/.lan(RobotAddress)/.remote/.simulated` — do **not** put `.lan`'s address in the activity.

Receiving side: the other device resolves identity → address through `KnownRobots` (`Sources/ReachyKit/Model/KnownRobot.swift:8–24`, `key`/`name`/`address`/`lastConnected`, keyed by `deduplicationKey`) and `CandidateSweep` (`Sources/ReachyUI/Connect/CandidateSweep.swift:85–99`, seeds `KnownRobots.lastAddress` first). Note `KnownRobots` is App-Group `UserDefaults`, per-device — a handed-off hardware ID may be unknown to the receiver, which is a case the plan has to name.

## Seams worth naming in the plan

- One arrival funnel already exists (`RootLifecycle.follow(_:)`) — a Handoff continuation is a third caller, not a new path.
- `ReachyDeepLink` cannot carry a robot, and widening it to take query items would also widen what the widget and Spotlight identifiers mean. A separate small `Codable` activity payload (`tab` string + `RobotIdentity`) that resolves *into* `ReachyRouter.Tab` + a connect request is the smaller diff and keeps `ReachyDeepLink`'s "exact parsing" property intact.
- `ReachyRouter.Tab` needs a stable string spelling; `ReachyDeepLink` only covers 2 of the 5 tabs (`robot`, `apps`) — `live`, `moves`, `settings` have no wire representation today.
- Per §3, the plist key lands on iOS and macOS simultaneously — no per-platform split to maintain.
- Project rule 4 (identity, never address) is already enforced by `RootLifecycle.connectedRobotID`; reuse it rather than reading `session.link`.</result>
